# The rules of conduct

The hard rules a worker in this tree keeps, read whole before any work; the rules the tree itself must satisfy are in [RULES.md](RULES.md), and the rules of landing, how a change reaches main, are in [LANDING.md](LANDING.md).

- The documentation rulebook is owned by the style. [CONVENTIONS.md](CONVENTIONS.md) and the rule documents it names change only inside the template itself, in the My-Styles repository and by its owner; a project derived from this template never edits its copy and never diverges from it. A derived project that believes a rule is wrong or missing sends the case upstream instead (see [REPORTING.md](REPORTING.md)).
- An agent sends nothing outside the repository on its own, no issue, message, pull request or upload, because what leaves the repository cannot be taken back; it proposes the sending as a numbered option in its closing note, and the owner sends or declines.
- A document the index names is read whole, first line to last, before it is relied on, never by its first and last lines or a slice from the middle, because a rule skipped is a rule broken without knowing; code is read as the task needs, and a record is read whole when it is cited. When the owner asks what a rule means, the agent quotes the rule's own sentence from the guide or the rulebook before it explains, because a paraphrase of a rule is a second copy of it, and a second copy drifts. A read a tool cut short, by truncating its output or failing to fetch, is re-read in parts until it is whole, or the closing note names the file as not read whole, and every fetch that failed is named there too, because a half-read file is a file skipped by a tool rather than by the reader, and the reader is the one who answers for it.
- An em dash is legal where it clearly beats the comma, the parenthesis, or the period it replaces, and it counts as its paragraph's one flourish. A tracked file carries at most two; the docs audit counts that boundary, so a tree with no remote is held to it as well, and it judges a record only from the commit the count's own scope sentence arrived in, because a record over the budget admits no edit that could bring it under; the judgment of fit and commit messages stay with review. A file a machine wrote and the tree keeps as written is declared `linguist-generated` in `.gitattributes` and stands outside the count, the spelling advisory and the vocabulary advisory.
- Commit history speaks in the owner's voice alone. No attribution trailers, no Co-Authored-By lines, nothing naming a tool or an assistant in a commit message. Held in review, like every commit-message rule.
- A check that makes a worker damage the work is worse than no check. When a rule fights something real, neither bend the work to earn a green run nor rewrite the rule. Pause the work in a state it can resume from, report the conflict, propose the change, and wait for the owner's explicit approval, because a rule change slipped into a busy diff is a decision nobody made. A length rule cuts filler and never information, a repair is verified for its side effects rather than for its intent, and a warning is answered rather than avoided, since an advisory a worker silences has become a gate. A question to the owner, here or in a closing note, is posed as numbered options, each stating in one sentence what the agent will do if it is chosen, with the recommended one marked, so the answer can be a number or a word; a reply that matches no option is restated in one sentence at the top of the next message, as what was understood and is about to be done, before anything is done. A finding the owner disputes is not re-judged in the context that heard the dispute, because a judgment that moves under argument alone has measured the argument; it goes to a reader who sees the finding and its evidence and not the exchange, another session or the owner, and the owner's decision ends it either way. A change in the tree this session did not make, a file edited, added, or moved by no act of its own, is another actor, a session or a tool, and is reported and left alone rather than repaired, because a repair of what one did not break undoes someone's work.
- A completeness claim names its boundary. Saying that every caller was updated or every usage fixed is a fact only when it names the enumerable list it exhausted, a grep, a file list, a suite run, that a reader can re-derive. A claim over a region the claimant drew itself, such as every edge case considered, is offered as judgment rather than fact, because no boundary exists for it to have reached and the claim reports only that the claimant stopped finding things. Review probes the second kind, and trusts the first only as far as its boundary reaches.
- Every closing note, the message that ends or pauses a task, opens with one state line, so the owner never has to infer whether the work is finished; an answer that only reads and explains needs none. `Done.` means nothing the task asks of the worker is left, and it is followed by `Nothing pending.` when nobody holds anything more, or by each item someone else still holds, the owner, another project or a person outside the session, named with its holder. `Waiting on you:` names what the work needs from the owner before it can go on, with the numbered options in the body where it is a choice. `Running:` names what the work set going and is still running when the note is sent, a gate, a CI run, a background command, and promises a report when it ends; a note never says done while one is. Work that both waits on the owner and is still running says both on the one line, the wait first. No tool can read a closing note, so the rule is held in review.
- When the owner asks for a TLDR, the reply is three lines and nothing else, each one sentence, even when the full answer is short; the full answer is the reply the TLDR follows, or the stretch of discussion the owner names. `Bottom line:` says what the full answer comes to, its answer, verdict or recommendation, and where the full answer was a task's closing note, it is that note's state line word for word. `Why:` says what the bottom line rests on, the source of a fact, the reason for a judgment, or the proof that work stands where the first line says. `Your move:` says what the owner must do or decide next, by option number where the full answer posed options, or `Nothing.` when nothing waits on the owner. Each line keeps its job whatever the answer is about, and a TLDR adds no claim the full answer did not make, with no line before the three and none after. No tool can read a reply, so the rule is held in review.
- All prose must read as if a person wrote it. Never write the clause-colon splice, a sentence shaped as claim, colon, elaboration; in prose a colon may only introduce a list, a quote, or a label. The softer language-model tells (balanced semicolon antitheses, triadic lists, not-X-but-Y reversals) are fine one at a time and forbidden stacked, so allow at most one flourish per paragraph and keep the rest plain declarative sentences. No tool can judge these, so they are held in review, agent and human alike. The full catalog of tells, the vocabulary, and the portability test live in the rulebook's Prose section ([CONVENTIONS.md](PROSE.md#prose)).
- Every tracked byte is public prose. Confidential facts, private repository names, deployment details, and the description of what was withheld and why never enter a tracked file or a commit message, even in a private repository, because visibility can flip and history is permanent. Such context goes to the untracked `LOCAL.md` at the root (see [BASELINE.md](BASELINE.md)); read it when it exists, create it when first needed, and when unsure whether a fact is sensitive, ask the owner instead of recording it. Where the working tree does not outlive the session, as in a hosted sandbox rebuilt from the repository, no `LOCAL.md` is created, because an untracked file is lost there without a trace and the next session reads its absence as nothing withheld. The worker puts the fact to the owner in the conversation, the owner keeps it outside the repository, and a session that needs one asks the owner for it.
- Read [STATE.md](../STATE.md) before starting work, and sweep it before starting anything new, deleting every entry that describes finished work and re-verifying or deleting any entry the tree no longer confirms. Its entries are claims to verify, not facts. Completing work deletes its entry in the same change, never adds a narration of the landing, and every change ends with a sweep for entries it completed or invalidated.
- Read [INVARIANTS.md](INVARIANTS.md) before changing what the site promises. It lists what must stay true, one row per claim, each with the holder that refuses a violation and the rung that says what its green is worth. A change that adds, moves, or retires a claim changes its row in the same change, a claim nothing decides is written with review as its holder so the audit prints it on every run instead of leaving it in memory, and no row says proved, because a sampled property is not a proof and a passing test is not a theorem.
